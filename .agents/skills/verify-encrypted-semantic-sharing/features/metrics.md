# Synthetic corpus scaling and retained metrics

Run `python -m semshare.benchmark --run-id <fresh-id> --cache-dir <isolated-cache>` on Ubuntu with the pinned research environment and hash-checked encoder. The manual metrics workflow uses a new runner and `.agents/metrics-model-cache`; no shared ML environment is modified. `--smoke` uses eight documents, one query and one repeat for correctness only.

The driver owns Launch, Doctor, Drive, retained Evidence and Cleanup using the maintained lifecycle. It uploads, shares, downloads, authenticates and embeds 64 synthetic documents through the actual app. Eight topic labels and four held-out paraphrase queries are frozen in `workload.json` before inference. Sweep endpoints are 8, 32 and the benchmark's frozen 64-document ceiling. The research ORAM supports up to 1024 records per index, but the full-application benchmark remains capped at 64. Each label has equal corpus representation. Documents and queries share labels but do not share exact text. These bounded synthetic labels support this workload's quality measurements only. [Hosted run 39733590445](https://github.com/STEVVVU/encrypted-semantic-file-sharing/actions/runs/39733590445) passed; the root README and `docs/evidence/metrics-39733590445/measurement.json` retain the measured slow path, queue growth and all cells.

Ingest schedules one document every 4.2 seconds. Each upload and public download consumes a file request, so this stays below the shipped 30-file-requests-per-minute limiter. The benchmark preserves that limiter and records the offered rate and scheduled latency. Search traffic goes to the sidecars and uses its separate load schedule.

Five alternating repeats compare encrypted delta and merged-epoch top-five queries with plaintext exact cosine ranking using the same float32 vectors. Every reference and score must agree. Recall@5, precision@5, MRR and nDCG@5 report observed held-out topic relevance. Ingest and index-build measurements are single samples and explicitly excluded from repeated comparison claims. Query embedding time is recorded separately and added to search latency; both sides use the same warm pinned CPU encoder. The plaintext baseline omits encryption, durability, ORAM and network and is a ranking overhead floor, not an equivalent privacy system.

The maximum corpus also receives five scheduled-arrival batches at concurrency/rate pairs 1/0.25, 2/1 and 4/4 queries per second. Each batch offers `max(32, int(rate * 10))` requests; the slowest rate spans at least 124 seconds. Tails include time queued in the bounded worker pool and behind the trusted-client lock; these scheduled arrivals do not establish that the service accepted the offered rate. Completed, rejected and erroneous requests have separate latency distributions and sample counts in `latency_by_outcome`; raw records remain intact. A lock deadline is counted as both a rejection and a timeout. Empirical p99 is omitted below 100 observations in that outcome. Sixty seconds of one-outstanding-query stability is a separate closed-loop check. Every measured result is checked against the exact oracle. Errors fail after recording outcomes. Profiles are separate queries, outside measurement samples. The workload records application payload bytes, sidecar payload bytes/messages, aggregate retained-index storage, client CPU/peak RSS and owned-process RSS snapshots. Payload counters omit HTTP headers and framing. Storage includes all corpus workspaces and retained whole epoch/delta trees; superseded path buckets are deleted after durable commit. It is neither active-corpus amplification nor cumulative historical write bytes. The historical raw storage scope incorrectly said no garbage collection; curated evidence corrects that wording without changing byte counts. Storage snapshots precede the scheduled-load stage.

The driver stops with preserved failure evidence if free disk drops below 10 GiB. Raw data, profiles and logs survive cleanup. No keys, embeddings, tokens or real documents enter evidence. Inspect all receipts before publishing medians/ranges, tails, limits or a limiter diagnosis. No formal privacy, MPC or paper-scale performance claims are supported.

## Index-only full-scan check

The full-application workload above remains frozen at 64 records and its published timing is a historical point-read scan result from source `e49209b`. The separate `python -m semshare.scan_benchmark --run-id <fresh-32-character-hex-id> --cache-dir .agents/model-cache` command exercises the current `Workspace.search` path against two owned loopback sidecar processes without starting the Go/CGO app or uploading files. It precomputes the fixed 1024-document corpus and four held-out query vectors in batches of at most 64, then performs five fixed rounds of all four queries. At 64 records it alternates the historical `records()` method from commit `72f07848a8133b36aece9a7e0816ce09f9b2e0f5` against the current snapshot method on fresh equivalent indexes; the old method is invoked through a temporary synchronous monkeypatch while current `open`, `read`, validation and cryptography remain active. At 512 and 1024 it measures the snapshot method only. The driver checks each top-five result against the exact float32-vector cosine oracle. Run B retains every actual and oracle rank pair; run A retains correctness flags but not the pairs. The 64-record point-read method made 2688 requests per query and sent and received 14,852,096 payload bytes in each direction. The snapshot method made 508 GET requests, sent no payload, and received 8,420,608 bytes. It left manifests and revisions unchanged. The empty workspace base index is included in that scan.

Runs `7e2e2f5d4fce4ae2923ddddb4579b8df` and `e4f6cfc7611944fa91d583a398a5ab52` completed all 80 queries with no errors or rejections. Their medians of five round medians at 64 records were 4.1747 s point-read and 0.4004 s snapshot in A, then 4.7976 s and 0.4643 s in B. At 512 and 1024, snapshot medians were 3.3072 s and 6.5588 s in A, then 3.7216 s and 7.4098 s in B. These are index-only timings, not full-app request or upload measurements. The [curated report and receipts](../../docs/evidence/scan-20261024/report.md) distinguish each run's range, request trace, payload volume, model and source hashes, and limits.

The driver requires the already cached, hash-checked MiniLM model and never downloads it. Retained receipts contain source, model, input and vector hashes and source copies, not model embeddings or prompt text. It saves all query samples, a separate 64-record CPU profile and source-line annotation, and copies both sidecar logs through the ownership-checked cleanup. It stops below 10 GiB free disk, above 1 GiB combined client/sidecar RSS, or after a cooperative 20-minute deadline. The initial run `4e45584e1e074178825b7ca30192c68f` stopped at that deadline after 31 of 80 query samples. Its partial receipts remain a failed campaign and supply no complete comparison result. The curated evidence retains its partial samples, hashes and failure record.

Use `--profile-only` with a fresh run ID for one diagnostic 64-record snapshot query on the same real model, Workspace search, and two owned sidecars. This mode creates only the 64-record fixture and does not run or summarize the timing campaign. Pre-pool diagnostic `25d64579821f4838a044dad0252fb274` attributed 4.362 of 5.448 profiled seconds to socket connection setup. Both complete campaigns used the pooled HTTPX client. Post-pool diagnostics `91d4a6a331e24ab8bfcc5c5e6ea4cc30` and `7fd2206ee4cb4479bf79e9fdf085d57d` passed the exact ranking, 508-GET, no-write checks and retained cleanup receipts. These profiler runs are diagnostics, not repeated benchmark measurements or a transport speedup claim. The full 80-query campaign and full-app integration remain separate checks. Run `python scripts/check_scan_receipts.py` to validate the curated results and recompute both summaries from the saved rows without writing to either original summary.
