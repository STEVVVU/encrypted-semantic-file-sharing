# Synthetic corpus scaling and retained metrics

Run `python -m semshare.benchmark --run-id <fresh-id> --cache-dir <isolated-cache>` on Ubuntu with the pinned research environment and hash-checked encoder. The manual metrics workflow uses a new runner and `.agents/metrics-model-cache`; no shared ML environment is modified. `--smoke` uses eight documents, one query and one repeat for correctness only.

The driver owns Launch, Doctor, Drive, retained Evidence and Cleanup using the maintained lifecycle. It uploads, shares, downloads, authenticates and embeds 64 synthetic documents through the actual app. Eight topic labels and four held-out paraphrase queries are frozen in `workload.json` before inference. Sweep endpoints are 8, 32 and the supported maximum 64 documents. Each label has equal corpus representation. Documents and queries share labels but do not share exact text. These bounded synthetic labels support this workload's quality measurements only.

Ingest schedules one document every 4.2 seconds. Each upload and public download consumes a file request, so this stays below the shipped 30-file-requests-per-minute limiter. The benchmark preserves that limiter and records the offered rate and scheduled latency. Search traffic goes to the sidecars and uses its separate load schedule.

Five alternating repeats compare encrypted delta and merged-epoch top-five queries with plaintext exact cosine ranking using the same float32 vectors. Every reference and score must agree. Recall@5, precision@5, MRR and nDCG@5 report observed held-out topic relevance. Ingest and index-build measurements are single samples and explicitly excluded from repeated comparison claims. Query embedding time is recorded separately and added to search latency; both sides use the same warm pinned CPU encoder. The plaintext baseline omits encryption, durability, ORAM and network and is a ranking overhead floor, not an equivalent privacy system.

The maximum corpus also receives five scheduled-arrival batches at concurrency/rate pairs 1/0.25, 2/1 and 4/4 queries per second. Each batch offers `max(32, int(rate * 10))` requests; the slowest rate spans at least124seconds. Tails include time queued behind the trusted-client lock. Completed, rejected and erroneous requests have separate latency distributions and actual sample counts in `latency_by_outcome`; raw records remain intact. A lock deadline is counted as both a rejection and a timeout. Empirical p99 is omitted below100 observations in that outcome, including the small paired query comparison. These sample minima do not establish a stable production p99. Sixty seconds of one-outstanding-query stability is a separate closed-loop check. Every measured result is checked against the exact oracle. Errors fail the run after recording outcomes. Profiles are separate queries, outside measurement samples. The workload records application payload bytes, sidecar payload bytes/messages, cumulative immutable storage, client CPU/peak RSS and owned-process RSS snapshots. Payload counters omit HTTP headers and transport framing. Cumulative storage includes all prior corpora and revisions; it must not be labeled active-corpus amplification. Old buckets are retained by the shipped product.

The driver stops with preserved failure evidence if free disk drops below 10 GiB. Raw data, profiles and logs survive cleanup. No keys, embeddings, tokens or real documents enter evidence. Inspect all receipts before publishing medians/ranges, tails, limits or a limiter diagnosis. No formal privacy, MPC or paper-scale performance claims are supported.
